# HAHAFS
## Структура проекта

```
./
  fs/         # out-of-tree + out-of-source кернел-модуль, содержащий код самой ФС

  fs_init/    # утилитная программа для форматирования файла в валидную hahafs
              # запускается на хост-машине

  fs_test/    # тестовые программы
              # - bash-скрипт, который читает и пишет случайные цифры в файлы ФС
              # - программа на c для запуска ioctl

  scripts/    # скрипты для скачивания и сборки кернела + запуска qemu.
```

### Расположение данных на диске
```
┌─────────────────────────┐0x0    |
│superblock #1            │       v
│─────────────────────────│0x1FF   
│inode block #1           │        
│─────────────────────────│     
│...                      │        
│─────────────────────────│        
│inode block #N           │        
│─────────────────────────│        
│file #1 block #1         │        
│─────────────────────────│        
│...                      │        
│─────────────────────────│        
│file #1 block #M         │        
│─────────────────────────│        
│file #2 block #1         │        
│─────────────────────────│        
│...                      │        
│─────────────────────────│        
│file #X block #Y         │        
│─────────────────────────│        
│superblock #2            │        
│─────────────────────────│        
│file #X block #Y+1       │        
│─────────────────────────│        
│...                      │        
│─────────────────────────│        
│file #N block #M         │        
│─────────────────────────│        
│empty space (less than M)│        
└─────────────────────────┘        
```

Каждый блок ФС занимает ровно один сектор диска. Первый блок отведён под первую копию суперблока. Вторая копия суперблока находится на некотором секторе K. При этом, этот сектор может находиться "между" секторами какого-то файла. В связи с этим, расположение файла на диске определяется стартовым сектором и "пропускаемым" сектором.

После первой копии суперблока идёт набор секторов, содержащих представление инод/дентри на диске (в кейсе этой фс разницы по сути нету, есть только рут директория и строго одна ссылка на каждый файл). Судя по диаграмме в условии задания хранение на диске мета-информации о файлах не предполагалось, но я не придумал как иначе сохранять информацию о размере, хэше и имени файлов и не терять их при анмаунтинге ФС/отключения модуля. Поэтому, для каждого файла на диске хранится следующая информация:
```c
struct hahafs_inode {
	__u32 hash;
	__u32 size;
	char name[];
};
```
При этом имя представлено free-array членом структуры и занимает max_file_len байтов (размер задаётся в параметрах модуля/суперблоке ФС).

В связи с этим, рассчитать, сколько файлов помещается на диске менее тривиально. Число помещающихся в секторе инод зависит от максимальной длины файла и "отнимает" часть секторов, которые могли бы быть заняты данными файлов.

Хэш файла перерассчитывается после каждой записи в файл (+ сбрасывается в ноль при clear вызове в ioctl).

Размер файла изначально задан как ноль и изменяется в соответствии с результатом записи в файл.

Имя файла задаётся при инициализации ФС и остаётся неизменным, ко указывается на диске.

### Расхождения с оригинальным условием задания
1. Задание - "Каждый оставшийся сектор должен соответствовать файлу"  
   Как было очевидно из предыдущего абзаца, это условие выполнено с точностью до набора секторов, занятых инодами.
2. Аргументы модуля - "Название диска на базе которого должна быть создана ФС"  
   Так и не понял, зачем предполагалось передавать в модуль аргумент с названием диска. Маунтить ФС в инициализации модуля звучит как плохая идея, ровно как и инициализация ФС в инициализации модуля. Поэтому, в моей реализации этого аргумента нет
3. Аргументы модуля - "Смещения N для superblock-ов (отдельно для первой и второй копии)"
   Это условие я тоже не понял, ранее писалось, что первая копия суперблока всегда в первом секторе, зачем задавать ей оффсет? В моей реализации передаётся один оффсет для второй копии суперблока
4. IOCTL - "Получить список всей метаинформации (хэши) из файлов"
   Получить список всех хэшей для всех файлов звучит как головная боль с выделением буферов достаточного размера, поэтому я решил сделать этот пункт ioctl по аналогии с четвёртым пунктом, т.е. с аргументом-именем файла
